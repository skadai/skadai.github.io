## 一句话结论

MoE 的核心思想只有一句：**把 vanilla transformer 里那个又大又厚的 FFN 切成很多份，每次只让其中几份参与计算。**
模型因此可以"装得下更多知识"而不需要"每一步都动用全部知识"。而它的代价也很具体：
**权重还是得全部装进显存**，并且多了一套"谁来干这单"的路由机制——路由挑得不好，模型就会变笨、变慢、甚至忽好忽坏。

## 从你熟悉的那层开始

在 vanilla transformer 里，每个 block 大概长这样：

```
x → LayerNorm → 注意力 → 残差 → LayerNorm → FFN → 残差
```

那个 FFN 就是"学知识"的地方：一个两层的小网络，把 hidden 维度放大几倍再压回来。
它的问题是**对每个 token 都一模一样地干活**——不管这个 token 是"的"还是"量子纠缠"，
都要经过同一个巨大的矩阵。

MoE 的改法：把这一个大 FFN 换成一排 FFN，然后给每个 token **动态挑几个**。

```
                ┌─ 专家 1
                ├─ 专家 2
token → 路由器 ─┼─ ...
                └─ 专家 384       每个 token 只走其中 6 个（外加 1 个 shared）
```

数学上就是：原本 `y = FFN(x)`，现在变成
`y = Σ w_i · Expert_i(x)`，其中只有 6 个 `w_i` 非零。

## 这里的三个关键设计

**1）384 里取 6，再加 1 个 shared expert。**
"取 6"是稀疏化的来源：算力只花在 6 份专家上。
那 1 个 **shared expert（共享专家）**是每个 token 都会经过的那一份，相当于公司的"公共知识部门"——
语法、高频词、通用推理这类所有 token 都用得上的东西，不必让每个专家各学一遍。
代价是：这 1 份的权重永远昂贵（永远被激活）。

**2）怎么打分：`sqrtsoftplus` 与 `noaux_tc` 偏置。**
路由器要计算"这个 token 该找哪几位专家"，就得给 384 个专家各算一个分数，再取前 6。
V4.1 用的是 `sqrtsoftplus` 作为打分函数，并带一个 `noaux_tc` 偏置项。
（"noaux" 指不需要额外的辅助损失来维持负载均衡，"tc" 指这套偏置是作用在 top-k 选择上的。）
你可以把它理解成**招聘时的历史口碑修正**：某个专家最近被叫得太频繁，就人为给它降一点分；
有的专家长期闲着，就抬一点——为了让 384 位专家不至于"有人累死、有人饿死"。
这个偏置是模型训练时学出来的，不需要你手动调，但**它解释了为什么推理时专家负载会随时间波动**。

**3）图像 token 走一套单独的路由偏置。**
页面上有一句容易被忽略但很重要的话：
> 对落在图像 span 内部的 token，使用**单独的**路由偏置——这样视觉 token 和文本 token 不会去抢同一批专家。

为什么要这样？因为图像 token 数量多、分布又和文字完全不同。如果不隔离，
图像一进来就把某几位专家挤爆，文字 token 只能退而求其次。分开之后，视觉和语言各有一套"熟练工"。

## 回到显存和部署：MoE 的真实代价

看一眼官方给的显存账本（第 9 篇会完整拆解）：

| 部件 | 参数量 | 存储 |
|---|---:|---:|
| 路由专家 + DSpark 专家（MXFP4） | 557.2B | 259.5 GiB |
| Engram 表（FP8） | 196.6B | 183.1 GiB |

两行加起来，就是这台机器上绝大部分显存。请注意一件事：**专家是"稀疏使用、但不稀疏存储"**——
每次只用 6 个，但 384 个都得待在显存里随时待命。
这就是为什么这类模型的部署第一难题是"装得下"，而不是"算得快"。

由此也引出三个部署动作，后面各有专篇：

- **专家并行（expert parallel / DEP）**：384 个专家不必都挤在一张卡上，可以按卡切。
  官方在 B200/B300/GB200/GB300 上就是这么干的（第 11 篇）。
- **量化**：路由专家用 MXFP4 存储（4 bit），其余用 MXFP8——**只量化"专家"，因为专家最多**（第 9 篇）。
- **MoE 内核选择**：AMD 上页面让命令传 `--moe-backend aiter`（让 vLLM 去挑 Composable Kernel 的 a8w4 专家内核），
  而 Blackwell 上则用 `deep_gemm_mega_moe`（第 13 篇）。

## 三个常见误解

**你以为：只用 6 个专家，所以显存只要 1/64。**
实际上：算力省了，显存没省。6/384 省的是 FLOPs 和带宽，384 份权重仍然要全部驻留。

**你以为：路由是随机挑的。**
实际上：路由是**学出来的、输入相关**的。同一个 token 出现在不同上下文里，可能被分给不同专家——
这也是 MoE 模型"行为不够可预测"的原因之一。

**你以为：专家多 = 一定更强。**
实际上：专家越多，路由越难学、负载越难均衡，通信成本（跨卡取专家结果）也越高。
384 取 6 是一个被工程约束反复调出来的平衡点。

## 术语卡片

| 术语 | 中文 | 一句话定义 |
|---|---|---|
| MoE | 混合专家 | 用多个小 FFN 代替一个大 FFN，每个 token 只激活少数几个 |
| routed expert | 路由专家 | 由路由器按 token 决定是否启用的专家（此处 384 选 6） |
| shared expert | 共享专家 | 每个 token 都会经过的那一个专家（此处 1 个） |
| router | 路由器 | 给 384 个专家打分并选出前 6 的小网络 |
| `sqrtsoftplus` | — | 本模型给专家打分的激活函数 |
| `noaux_tc` bias | 路由偏置 | 训练学出的负载均衡修正项，防专家过载/闲置 |
| image routing bias | 图像路由偏置 | 图像 span 内 token 专用的一套偏置，避免与文本抢专家 |

## 小结

1. **MoE 省的是计算，不是显存**——这句话决定了后面所有部署权衡。
2. **6（路由）+ 1（共享）**是稀疏度的来源；共享专家负责公共知识，路由专家负责专精。
3. **路由是学出来的、带均衡偏置的，而且图像和文本各有一套**——所以它既强大又难以完全预测。
